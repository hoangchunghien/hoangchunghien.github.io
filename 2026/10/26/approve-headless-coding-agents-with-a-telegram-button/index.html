Approve What Your Headless Coding Agent Does With One Telegram Button

Posted on 2026-10-26 In AI Engineering

The problem with letting agents run unattended

I run several coding agents headless on my workstation. One reviews pull requests, one implements tickets from a written plan, one watches repositories and regenerates documentation when the code moves. They run as claude -p processes started by systemd timers and shell scripts, which means nobody is sitting at a terminal when they finish.

Most of their work is safe to do alone: reading code, running tests, writing a report to disk. A few steps are not. Posting a review comment under my name, pushing a branch, opening a PR, deploying to a shared environment. Those are outward facing and hard to take back, and I want to see them before they happen.

The usual answers did not fit. A permission prompt needs a terminal. Email is too slow to act on. A web dashboard is one more thing to keep running. What I already had open all day was Telegram on my phone, and Telegram bots support inline buttons. So every risky step became a message with Approve, Show and Skip under it.

After running this for a few months, the shape that works is small: three scripts and a directory of JSON files.

The shape

  1. The agent does its work, writes the draft (a comment, a PR body, a plan) to a file, and registers a pending item: a JSON file that says what kind of action it is and what it needs.
  2. offer.sh sends the draft to Telegram with three buttons whose callback_data carries the item id.
  3. A long-running bridge is the only process polling the bot. When a button is tapped it calls action.sh <verb> <id>.
  4. action.sh does the publishing for that kind of item and replies with one line of status.

The agent never publishes anything itself. It can only propose.

The pending item

The kind matters more than it looks. It is tempting to store a shell command in the item and run it on approval. That is convenient and a bad idea: anything that can write a pending file can now run arbitrary commands the moment I tap a button on my phone, usually without reading closely. The current version has a fixed set of kinds, and each one maps to a publisher function written by hand. The item supplies data, never code.

Sending the offer

Two limits to know about: a message is at most 4096 characters, and callback_data is at most 64 bytes. Keep the id short and put everything else in the file. For long drafts I send a preview in the message and let Show send the whole file as a document.

The bridge

Telegram allows only one getUpdates consumer per bot. If two scripts poll the same bot, they steal each other's updates and buttons appear to do nothing. So there is exactly one bridge, and every agent's buttons go through it with a prefix per agent.

Three details in there earned their place by breaking:

  • Persist the offset. Without it, a restart replays the last day of taps and approves things twice.
  • Answer the callback. If you do not call answerCallbackQuery, the button spins on the phone for a while and you tap it again.
  • Check who tapped and what the id looks like. The id ends up in a file path. Allow only safe characters.

I run the bridge as a systemd user service with Restart=always and lingering enabled, so it survives logouts and reboots.

The action handler

The status check before publishing is the double-tap guard. Phones lag, people tap twice, and without it you post the same comment twice. Moving to publishing before the slow call means a second tap that arrives mid-publish sees publishing and stops.

Gating a step in the middle of a run

Sometimes the agent should not just propose and exit. The ticket-implementing agent writes a plan, and only after I approve the plan does it start changing code. For that the agent offers the plan, then waits on the file:

For the waiting case, the action handler only stamps the decision instead of publishing. The agent reads it and carries on. A file on disk is the whole protocol, so I can approve from the shell with jq when my phone is not around, and I can see every decision afterwards with ls pending/.

What I would tell someone building this

  • Keep the agent's permissions and the approver's permissions apart. The agent writes drafts. A separate, boring script holds the tokens that publish.
  • Show the real thing. Approving a summary of a comment is not approving the comment. Send the exact text that will go out, or the diff.
  • Make Skip cheap. If saying no is more work than saying yes, you will start saying yes.
  • Log decisions. An append-only history.jsonl with what was proposed, what I chose and when has been more useful than I expected, mostly for noticing which kinds of proposal I skip and fixing the agent that makes them.

The whole thing is a few hundred lines of Bash, jq and curl. It has been the difference between agents I check on and agents I trust to run while I sleep, because the parts that matter still wait for me.
